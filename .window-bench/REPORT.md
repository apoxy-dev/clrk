# Window/ROB falsification: CORE_BOOT vs the microarchitecture

Generated by `scripts/analyze.py` from `results_adapted`. Mechanical verdict; no value below is imputed -- a test that did not run on a host is excluded from its aggregate and listed as skipped.

Hypotheses under test:

- **H1 (window-bound):** a bigger ROB/LSQ would cut CORE_BOOT; the window is the binding resource.
- **H2 (memory-bound):** CORE_BOOT is set by effective memory access time (DRAM/L2 latency + TLB/page-walk), imperfectly hidden by *true* MLP (LFB/MSHR count, NOT the ROB) + prefetch, plus a clock-scaling compute remainder. ROB is a non-causal correlate.

## Verdict (analyst synthesis, authoritative)

**Both H1 and H2 are FALSIFIED. gVisor cold boot is frontend/instruction-supply + core-execution
bound, with negligible DRAM exposure -- it is neither window/ROB-bound (H1) nor DRAM-latency-bound
(H2).** The blog's ROB<->CORE_BOOT rank match is a confound, not a cause.

### Patched re-run (membarrier sync.Once) -- added after review

The original CORE_BOOT numbers were taken with STOCK gVisor, so they carried the hostmm/membarrier
`synchronize_rcu` grace-period tax (a full boot fires ~9 `REGISTER_PRIVATE_EXPEDITED` calls). Re-built
`bench-runsc` against the validated sync.Once patch (`hostmm.init` confirmed ~0) and re-measured:

| host | stock CORE_BOOT | patched | RCU/membarrier tax |
|---|---|---|---|
| c7i.metal-24xl | 176.3 | **100.1** | -76.2 (43%) |
| c7g.metal      | 208.3 | **129.2** | -79.1 (38%) |
| c7i.xlarge     | 150.5 | **112.1** | -38.4 (26%) |
| c7g.xlarge     | 154.3 | **123.4** | -30.9 (20%) |

Two consequences. (a) **The decisive TMA is unchanged on the patched boot** -- Intel metal: Frontend
27.8%, Backend 30.3% (Core 13.4 / L1 11.0), `STALLS_L3_MISS` **0.68%**, IPC **1.82**. The membarrier
tax was off-CPU sleep, not compute, so the frontend-bound / no-DRAM finding is robust and now sits on
clean wall-clock. (b) **The tax was much larger than first reported (20-43% of CORE_BOOT, not ~5-17 ms)**
and it scaled with core count, which is what made the metals look slow and made the matched-core ROB
comparison (item 3 below) read "flat" -- see the correction there.

The mechanical engine below returns INCONCLUSIVE because the *pre-registered* binary (window vs memory)
and its T1 threshold (memory_bound >= 40% AND core_bound <= 10%) did not anticipate a third answer,
and the two cleanest collinearity breakers (T2 frequency sweep, T3 remote-NUMA) were unrunnable on
these EC2 hosts (no settable cpufreq; single NUMA node). The decisive evidence is in the raw counters,
which point the same way on both arches:

**1. The boot incurs almost no DRAM-miss stalls -> H1's mechanism cannot operate.** On the Intel metal
(toplev, system-wide, GOMAXPROCS=4, 200-boot loop): `CYCLE_ACTIVITY.STALLS_L3_MISS` = **0.6% of
cycles**, IPC = **1.81**. H1's claim is that a bigger ROB overlaps more outstanding DRAM misses (MLP).
There are essentially no DRAM misses to overlap. The TMA tree:

```
Retiring        ~38%   |  Frontend_Bound 27.6%  (Fetch_Latency 15.4: MS_Switches 9.1, Branch_Resteers 7.2)
Bad_Spec        ~1%    |  Backend_Bound  32.8%  -> Core_Bound 15.1% (Serializing 20.4%clk, Ports 18.3%clk)
                       |                        -> Memory_Bound ~17.7% but L1_Bound 11.5%; L3/DRAM ~0
DTLB walk active = 2.0% of cycles. The single largest non-retiring bucket is FRONTEND (cold i-cache /
iTLB / branch resteers / microcode on gVisor's huge code footprint) -- a channel NEITHER hypothesis named.
```

**2. Disabling all four hardware prefetchers does nothing -> latency is not being hidden.** Intel metal,
MSR 0x1A4 = 0xf on cores 0-3: CORE_BOOT p50 181.7 -> 182.1 ms (**+0.39 ms, +0.2%**). If the boot were
DRAM-latency-bound with prefetch overlapping misses, removing prefetch would expose that latency. It
does not move -> not prefetch/latency-hidden (kills a core H2 channel).

**3. The cross-core CORE_BOOT comparison cannot isolate the ROB (CORRECTED).** The first draft claimed
"doubling the ROB at matched cores buys nothing (c7g.xlarge ROB 256 = 154 ms vs c7i.xlarge ROB 512 =
150 ms, flat)". That was an RCU-contamination artifact: those stock numbers each carried ~30-38 ms of
membarrier tax. **Patched (clean): c7i.xlarge (ROB 512) = 112.1 ms vs c7g.xlarge (ROB 256) = 123.4 ms**
-- the bigger-ROB core is ~11 ms (9%) FASTER, not tied. But the Intel also clocks 3.8 vs 2.6 GHz and is
a different ISA, so this 9% is clock/ISA-confounded and is NOT a clean ROB test in either direction.
Conclusion: the wall-clock cross-core comparison is too confounded (clock, ISA, RCU) to isolate the ROB;
it is dropped as a falsifier. The mechanism-level evidence (items 1, 2, 4) carries the verdict and does
not depend on it.

**4. The measured miss-concurrency ceiling sits far below the ROB.** Measured MLP knee = 6 (x86*),
16 (Neoverse V1), 20 (Firestorm) -- i.e. true outstanding-miss concurrency (an LFB/MSHR property) of
~6-20, which is 13-100x below the ROB sizes (256-630). The ROB is never the binding constraint on miss
overlap even where misses exist; the LFB/MSHR count is. (*x86 knee is a floor: the bench used a 128 B
line stride, correct for the M1 but coarse on 64 B-line x86, so it likely under-measures x86 MLP. This
does not affect the verdict -- with 0.6% DRAM-miss stalls, MLP capacity is moot for this workload.)

**Why the blog's rank match still appears:** a bigger, "better" core (M1 Firestorm) is wider and faster
*everywhere* -- 8-wide decode, deeper OoO, bigger/faster L1+L2, better branch prediction -- and ships a
bigger ROB as one feature of that balance. Its ~2x CORE_BOOT lead (78 vs ~150 ms) is bought by its wide
frontend + fast near caches + execution width on a frontend/core-bound workload, NOT by overlapping DRAM
misses. ROB rank-correlates with CORE_BOOT because it correlates with "big wide core", which is the
textbook non-causal confound H2 predicted -- but the binding resources are frontend and execution, not
the data-memory subsystem H2 itself named. So the adversarial design did its job: it disproved BOTH the
blog's hypothesis and the reviewer's.

**Caveat -- ALL stock CORE_BOOT is membarrier/RCU-contaminated (quantified by the patched re-run).**
Every host pays the hostmm/membarrier `synchronize_rcu` tax, and it is large and core-count-scaling:
the patched re-run measured it at 30-38 ms on the 4-vCPU xlarges and 76-79 ms on the 64/96-core metals
(20-43% of stock CORE_BOOT). This is a kernel wall-clock cost unrelated to ROB or memory. So any
wall-clock cross-host comparison must use the patched numbers; the metals' apparent slowness in the
stock data was mostly this tax. The TMA / prefetch / microbench evidence is cycle-attributed (toplev
counts unhalted cycles), so it is immune to the off-CPU RCU sleep and unchanged by the patch.

**Confidence.** HIGH that the boot is not DRAM/MLP/ROB-bound: two mechanism-level measurements (L3-miss
stalls 0.6-0.68% stock and patched, prefetch-off null) agree on the decisive Intel metal and are corroborated
on Arm (memory_bound 10.7-12.1% < core_bound 17.1-18.9%, dtlb_walk 0.05%). MEDIUM on the precise
frontend-vs-core split (the whole-loop TMA includes kernel fork/exec/syscall paths, not only the Sentry
Go boot -- though CORE_BOOT *is* that whole workload, so the attribution targets the right metric).
The Spearman block below is NOT load-bearing (n=5, RCU-contaminated metals, M1 CORE_BOOT taken from the
blog since gVisor is Linux-only; its negative DRAM-latency rho is causally nonsensical = small-n noise).

**What would still strengthen this:** a settable-frequency host (Test 2, to split the clock-scaling
compute term `a` from a memory floor `b`); a multi-socket metal (Test 3 remote-NUMA); a per-phase TMA
that isolates the Sentry Go boot from the kernel syscall path; and an x86-line-size-correct MLP re-run.

## Methodology / honesty notes

- CORE_BOOT is `runsc create` + `runsc start` of `/bin/true` from `cmd/bench-runsc`, Sentry pinned GOMAXPROCS=4 via `taskset -c 0-3`, >=50 timed iters after >=5 warmups, p50 reported.
- T1 memory_bound/core_bound are the level-3 backend split (toplev on Intel, topdown-tool on Arm); thresholds: reject H1 when memory_bound >= 40% and core_bound <= 10%.
- T2 fits CORE_BOOT(f)=a/f+b; b is the clock-invariant memory floor; b >= 40% of CORE_BOOT@nominal supports H2.
- T3 counts a CORE_BOOT shift >= 3.0 ms under remote-NUMA / hugepage / prefetch-toggle (ROB fixed) as movement supporting H2.
- T4 Spearman compares datasheet ROB/LSQ against measured DRAM latency / MLP knee as orderers of CORE_BOOT.
- No measurement is fabricated or interpolated. Skipped tests are excluded, never imputed.
